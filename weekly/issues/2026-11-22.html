MaskPE：装权重时恢复位置，执行时复用掩码关掉无效乘积

MaskPE: One Mask, Two Roles: Weight Placement and MAC Gating in Systolic Arrays

论文预印本，arXiv:2611.26432v1，2026-11-19 17:08 UTC（北京时间 11 月 20 日 01:08）提交。Shu-Lin Shih、Chandra Sekhar Mummidi、Aamir Gujral Elhaissouni、Sandip Kundu，均署名美国马萨诸塞大学阿默斯特分校。未找到独立的公开代码入口。版本记录 · 公开全文

一列权重为什么不能直接压紧

在权重驻留阵列里，每个处理单元（PE）先装好一个权重。计算时，激活值和部分和沿固定方向逐拍传给相邻的 PE。某个 PE 收到自己的激活值后，用驻留权重做乘法，再把乘积加到传来的部分和。这里的「部分和」就是已经加了前几项、还要继续往下传的累加值。可以把一列权重理解为一个输出通道要用到的一批系数。

假设其中四个权重是 [5,0,3,0]，相应激活为 [2,4,7,9]。正确结果是 5×2+3×7=31。只把压紧后的 [5,3] 塞给相邻位置，会把第二个非零权重交给接收 4 的 PE，结果变成 22。剪枝删掉的是权重的存储值，原位置对应的激活和部分和仍沿原来的路线走。

创新点与实现细节

  1. 同一份 bitmap 用两次。 每列解码器扫描 bitmap。遇到 1 就从非零值 FIFO 取一项，发出 (weight,sel=1)。遇到 0 就发出 (0,0)，FIFO 的读指针停在原处。每列都输出 32 项，用固定 32 拍装入阵列，无需先在片上存储器里拼出一份稠密权重，再转存给 PE。PE 把 sel 和 weight 一起保存，后面的激活可以反复使用这两项状态。论文的贡献在于把压缩值定位和乘积寄存器使能接到同一个位置位上。解码器 · PE
  2. 关闭寄存器时钟后，还要挡住旧乘积。 valid_in && sel 控制乘积寄存器是否更新。例如上一个 tile 在某个 PE 留下乘积 21，下个 tile 的权重为零。此时停钟会让寄存器仍读出 21。MaskPE 用 sel 屏蔽扩展到 INT32 的乘积，让累加器在该位置加 0。部分和寄存器由延迟一拍的有效信号控制，激活仍转发。论文因此保留原阵列的节拍，同时少翻转一部分寄存器和时钟树。乘法组合逻辑和累加路径的能耗还要单独算。PE 数据通路
  3. 让供数承受不规则访问，阵列按固定节拍工作。 非零 INT8 值紧密排列，列与列之间不补齐。每个 tile 的目录花 27 B：3 B 存起始地址，另用 32 个六位字段存各列的非零数。先对列计数求前缀和就能找到各列的起点。例如前两列分别有 3 和 5 个非零，随后一列从值流偏移 8 B 处开始。双槽表保存各列偏移，算当前 tile 时可以准备下一份。32 列的读请求共享 8 个各有一个读口的 bank，碰撞按轮转仲裁。bank 返回 32 位字，地址最低两位挑出所需 INT8，再进各列的缓冲。每列解码端可缓冲两个 bitmap 字节，值 FIFO 深度也是两项。碰到 1 时 FIFO 为空会报 underflow，解码器不会等数据再走下一拍。供数验证要问最堵的一列能不能赶上预装。地址和仲裁 · 预装次序

一次 TLB miss 为什么会挤到别的程序

TLB 缓存的是已经完成的地址翻译。TLB 没有命中时，硬件页表遍历器（walker）从上一级页表指针读到下一级，最终从叶页表项（PTE）得到物理页帧号和权限。上层描述符可能已被页表遍历缓存记住，最后一级依然需要读。以 4 KiB 页和 8 B PTE 为例，64 B cache line 装八个叶 PTE，因此一次填充覆盖 32 KiB 虚拟空间的翻译。这里的 64 B 是页表记录的存储量，32 KiB 才是这组记录能翻译的地址范围。

例如图计算程序沿着指针访问很大的数据集，会在共享 L2 留下大量叶行。同一期间，另一个核可能反复读取一个本来能留在 L2 的小工作集。若总给叶行更高的保留优先级，前一程序的 walker 少等了 DRAM，后一程序却要从 DRAM 把自己的数据重新拿回来。LeafPack 让 walker 标出叶访问，在共享缓存里缩小规则叶行的驻留表示。内存中的 64 B 页表行和 walker 的遍历算法沿用原来的格式与语义。问题与翻译层级

创新点与实现细节

  1. 先压行内，再决定能否跨行共享描述符。 假设八个 PTE 的物理页帧号是 100 到 107，八个描述符都有效，权限、访问位、脏状态及软件自用位也相同。存下第一个 8 B PTE，重建时把页帧号逐项加一，其他位照抄即可。若第三个 PTE 无效、权限不同，或者物理帧跳到了 300，整行需要保留完整 64 B。Packed 给每条可压行留自己的起始描述符，行与行可以有不同的权限和起始帧。Dense 在同一页表物理区域内共用一个基准描述符，另外存每条叶行开头的有符号 20 位帧偏移，范围约为 ±2 GiB。举例说，下一条规则行若从物理帧 140 开始、属性与基准一致，存偏移 +40 就能恢复它。两种方式都允许单条行内部的覆盖范围保持不变。压缩条件与两种编码
  2. 让压缩行能定位、也能单独失效。 页表所在的物理地址先按 1 KiB 对齐划成区域。这里的地址指 PTE 本身放在哪，和 PTE 所映射的物理页地址是两回事。普通查找用原来的 set 索引，压缩查找还检查用区域前缀算出的 packed set。该区域的 16 条行用地址位 [9:6] 编号，命中必须同时匹配区域标签和该行的有效位。于是，对某条叶行的失效只需清自己的有效位，同槽其他行仍可命中。写入时如果仍符合编码就原位更新。写入破坏编码时，可以把该行展开到原槽并逐出其余行。若同槽另有未完成的 miss，论文给出把更新行写回内存的路径。相反，替换策略的淘汰单位是整槽，一次可能逐出多条叶行。这里要分别检查一致性和替换两条路径。查找与替换 · 一致性与写回
  3. 按实际访存行为决定页表可占多少路。 控制器用少量 leader sets 采样，把压缩 15 路、压缩 5 路和未压缩 3 路三个上限放在同一组负载下比较。压缩候选各用 32 个真实采样 set，另用 shadow tags 估算不压缩时会不会命中。计数器按各核的 L2 访问频率给 miss 加权，让访问较少的同跑程序也能影响决策。上限调低后，超额组仍能命中，直到应用数据缺路时才回收。若写缓冲装不下待写回的行，就保留该组，后续再继续。这样切换上限不必一次清空整个缓存。控制器与组回收

  • 页表 miss 几乎消失，混跑还能变慢。 在 pr+gcc 上，pr 的遍历 miss 从 137 万降到约 1 万，恢复进度后它发出更多会 miss 的数据访问。gcc 的数据被挤出，指令访问进度从 145 万降到 116 万。作者比较了 DRAM 读延迟、总线利用率及 gcc 的 L2 数据 miss，主要限制落在 L2 数据容量。类似试验应同时报告每个程序的 IPC、数据 MPKI 和 walker miss，尤其要看平均数里谁变慢了。与 gcc 混跑的反例

  • 建议做单行状态回归。 在同一 Dense 槽放两条规则叶行，先失效一条，检查另一条仍能重建。再单改一个 PTE 的权限，同时在同槽其他行制造尚未完成的 miss，检查写回后的内容、可见性和是否只留一个可达副本。做空间或延迟比较时，固定 TLB、L2 大小与负载，分别扫物理帧碎片和数据敏感的同跑程序，记录组占用、回收写回次数与每核减速。

LLVM：向量 gather 的目的寄存器分开以后，异常重启才保得住索引

来源类型：开源编译器补丁。LLVM 项目；Craig Topper。PR #224739 于 2026-11-20 06:40:09 UTC（北京时间 14:40:09）合入主干，固定提交 a464c446768291a143deb9b3ee7877f159cb4700。这是主干实现，不能据此声称某个已发布 LLVM 版本已包含修复。提交与完整差分 · PR 说明

问题　一次 vluxei32.v 从向量寄存器取索引，再将各地址的数据写回目的向量。补丁说明：部分 SiFive 核在非零元素触发异常时，可能先改写目的寄存器中该元素以及后续活动元素。如果目的与索引寄存器重叠，这些写入就可能破坏尚待使用的索引。处理程序修好页映射后，即使从记录的 vstart 继续执行，后面的地址也已失真。关键不是异常前写了多少结果，而是重启需要的输入是否仍在。

方法　Clang 增加 -mfix-sifive-mal-9174 和别名 -mfix-sifive-mal-9191，各有对应 -mno-fix-… 关闭选项；sifive-p870-d CPU 模型默认启用。后端在选择指令后，将有序 vloxei*.v 和无序 vluxei*.v 的目的操作数标为 early-clobber，告诉寄存器分配器该定义可能在源使用完之前发生，因而不能让目的组覆盖索引源。它改变的是编译器的架构寄存器分配约束，不等于给硬件增加 VRF 端口或重命名资源。开关与别名 · 后端约束 · P870-D 默认配置

纯函数的最小实现 
function buildLedger(rows) {
  const groups = new Map();
  for (const r of rows) {
    if (!r.id || !r.source) throw Error('missing provenance or ID');
    const g = groups.get(r.id) || {
      id: r.id, owners: new Set(), dates: new Set(), sources: new Set()
    };
    g.owners.add(r.owner); g.dates.add(r.due); g.sources.add(r.source);
    groups.set(r.id, g);
  }
  return [...groups.values()].map(g => ({
    id: g.id, owners: [...g.owners], dates: [...g.dates],
    sources: [...g.sources], conflicts: [
      g.owners.size > 1 ? 'owner' : '',
      g.dates.size > 1 ? 'due' : ''
    ].filter(Boolean)
  }));
}

flush=0，valid=1，ready=1 只消费一次；若允许同拍补充，按冻结的上游握手接收新事务

产物与效果。 这张契约表、接口假设、候选 diff 和功能反例应与 PPA 报告一起交付。模型可以提出共享算术器、减少中间寄存器或调整流水线；每个候选先过功能与协议检查，再在相同约束和库下比较面积、关键路径与功耗。OpenAI 的数值为厂商披露，本刊未取得其 RTL、约束及完整测试制品；表中的单槽例子是待实施的回归方案，没有声称本期运行了形式工具。

可借鉴。 给模型的任务可以限定为：“先列所有状态转移和采样拍；保持背压时 payload；flush 优先于接收；列出同时 flush、ready、上游 valid 时的结果；接口语义冻结后一次只改一处。”人工复核 SVA 使用的是采样前还是更新后状态，确认 formal 假设没有排除背压与 flush 交错。若要承诺 flush 后系统内旧事务永不写回，还需把事务标记和下游在途状态纳入检查，单槽清 valid 并不足以证明这一点。

AI 辅助处理器架构设计：用 IPC 和关键路径共同筛选 BOOM 改动

From Seed to BLOOM: Autonomously Growing a Better Out-of-Order Core

论文预印本，arXiv:2611.26517v1，2026-11-19 17:59 UTC（北京时间 11 月 20 日 01:59）提交。Angela Cui、Ferran Hermida-Rivera、Jack Toubes（前三位共同贡献）、Jim Fang、Chengyi Lux Zhang、Borivoje Nikolić、Christopher W. Fletcher、Sagar Karandikar 均署名加州大学伯克利分校。作者称 MiracleGro loop 将来开源，目前论文不是已发布代码制品的证明。版本记录 · 公开全文

每拍退休更多指令，程序也可能跑得更久

BLOOM 是论文在现有 BOOM 上改出的乱序核，MiracleGro 是负责提出改动、写 RTL 和筛选版本的流程。作者从一个优化过关键路径的四发射 BOOM 开始。基线 ISA 为 rv64imafdczicsr_zifencei_zihpm，地址翻译采用 Sv39。ROB 有 128 项，访存、整数、浮点发射队列分别有 24、40、32 项。L1 D-cache 为 32 KiB，有 16 个 MSHR。L2 为 4 MiB、四 bank，每个 bank 有 22 个 MSHR。MSHR 记录缓存里还没拿到结果的 miss。配置表给的是标量核，本实验的结果适用于这套 BOOM 和相应负载。基线参数和综合方法

IPC 是每个周期平均退休的指令数。一段程序的指令数固定时，执行时间约等于「指令数 ÷ IPC × 周期长度」。例如原方案每拍退休 1 条、每拍 1 ns，100 条指令要 100 ns。改成每拍退休 1.74 条，若时钟必须拉长到 2.5 ns，反而要约 144 ns。这个手算对应论文里一个真实取舍的量级：只追 IPC 的合并候选 m16c0 约提高 74%，但关键路径拉到了基线的 2.5 倍。发生退化的合并候选

创新点与实现细节

  1. 让代理按电路结构找问题，再用 trace 缩小范围。 早期循环从性能计数器里挑最大的瓶颈，提案常集中在前端和内存。后续版本给不同代理分派具体结构。最终运行每轮分析四个结构方向，同时运行两轮。反馈包括计数器，以及抽样的流水线与内存事务 trace。作者发现，只有大类计数时很难判断是哪条请求阻塞，原始 VCD 又细到容易让代理只找佐证。抽样 trace 可以用同一条指令或请求把取指、执行和访存的事件对起来。代理还会写低保真的局部模型，先用当前设计的 trace 复核，再试换参数。只对齐了一个设计的模型，在改硬件以后还需重新校准。提案与观测 · 计数器与 trace · 局部模型
  2. 在综合结果出来后再给候选排序。 实现代理写 Chisel RTL，时序代理读关键路径并做局部 A/B。评估用的脚本、测试和预期结果放在代理不能改的环境中。多个改动合并后也重新跑评估，因为组合逻辑可能在模块交界处接成一条更长的同拍路径。m16c0 就把早先的低延迟 miss 路径和预取改动连在一起，从 ROB 经数据缓存 MSHR、L2 预取器和 SoC 总线到 LSU。其中光是让总线请求和响应在一拍内走完，就约占这条关键路径的一半。实现与合并流程 · 合并后的时序路径
  3. 搜索时跑代表片段，收尾时跑完整输入。 作者用 SimPoint 把 SPEC CPU2017 整数负载分成 1000 万条动态指令的区间，再抽取代表性片段。进入迭代的 128 个检查点，每个先预热 2000 万条，再测 1000 万条。作者事先去掉了基线上单次要超过四小时的检查点，整套片段不到 40 亿条动态指令。最后用 FireSim 跑完整 SPECspeed 2017 整数参考输入，总计超过 30 万亿条指令，并检查输出。这个阶段遇到的少数复杂错误需要人工指导。论文称将公开 MiracleGro 循环，当前条目只依据预印本所披露的流程。样本选择 · 完整输入与人工复核

两个值得回看的硬件改动

  • 关掉取指前递后，少掉的 IPC 换回了时钟频率。 迭代 11 的长路径从 TAGE 分支预测器的 SRAM 出发，经取指级和取指缓冲，到译码侧的分支掩码逻辑，最后回到取指缓冲的尾指针。加宽缓冲、提前预测和绕过缓冲直送译码，把原先分开的逻辑接到了一起。迭代 16 关掉提前预测和直送后，相对迭代 11 的关键路径缩短 47%，IPC 降 3%。拿这两个比例手算，同一指令数下执行时间约为原来的 0.53 ÷ 0.97 ≈ 0.55。这给出了为何要同时看周期数和综合周期的量级。前端路径取舍
  • 多个 L2 bank 都在发请求，DRAM 模型却按 ID 排队。 某个迭代的 L2 有 80 个 MSHR。代理看见来自不同 bank 的 demand miss 在内存 trace 里接连完成，再查 MSHR 占用与带宽，最后追到 AXI ID 分配。各 bank 优先用较小的 ID，容易让并发请求碰到同一 ID。实验用的 DRAM 模型把这些同 ID 请求串行处理。候选改用在途请求尚未占用的 ID 后，作者报告每个负载的 L2 miss 相关周期指标下降 7% 至 32%。此指标用「至少有一个 L2 demand miss 在途的总周期数 ÷ L2 miss 次数」计算，方便比较等待和重叠程度。写微基准时可以固定 bank 数与 MSHR 深度，观察碰撞 ID、每周期可重叠请求数和端到端延迟。内存请求串行的复盘

可以从一条路径开始试

给 AI 一段公开 BOOM RTL、一个可手算或对照参考实现的微基准，以及同次运行的计数器、trace 和综合路径。任务写成「从 trace 找一条等待链，指出两端模块与中间资源，提出一处 RTL 改动，并预测哪个计数会变」。先固定 ISA、发射宽度、ROB、缓存参数、综合库和约束。用同一测试跑修改前后版本，核对输出、退休指令数、周期数、周期长度及面积，按 cycles × clock_period 排名。

如果两个候选各自过关，至少再跑一次合并后的综合和功能回归，重点盯两者接在一起的模块边界。若预取优化只让 MPKI 下降，接下来查需求 miss 的等待拍、预取命中延迟和 tag 端口争用。作者就观察到一种情况：预取器要等 LSU 不读 L1 data tag 才能使用端口，访存繁忙时很少轮到。迭代 29 复制 tag 阵列获得并行访问，在 gcc 中相对其父版本让 L1D MPKI 降 26%，IPC 只增 1.6%。要移植这个思路，应先量化端口等待，再决定复制 tag 的面积是否划算。预取与 tag 端口案例
